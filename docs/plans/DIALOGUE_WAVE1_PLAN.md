# Dialogue Wave 1 plan — domain contracts and prepared bundle

## Execution model recommendation

Use **Sol X-High** in the Codex runtime. Execute sequentially because the core
contracts and prepared-manifest shape constrain all runtime and save work.

## Fixed interfaces

- `DialogueKey`, `DialogueChoiceId`, and `DialogueSessionId` are stable,
  serializable domain identifiers.
- `DialogueStartRequest` contains dialogue key, stable speaker/listener IDs,
  and a start source.
- `DialoguePhase`, `DialoguePresentation`, line presentation, option
  presentation, and structured dialogue errors remain Yarn-free.
- `PreparedDialogueBundleRef` contains schema/revision data, sorted source
  paths, bundle hash, node-index path, and optional voice/localization paths.

## Implementation boundaries

- Keep core contracts in `bevyout-core`; keep Yarn types in the later viewer
  adapter.
- Extend the prepared manifest with serde defaults for old manifests and bump
  the prepared revision/schema for the new serialized shape.
- Keep `dialogue/generated/` and `dialogue/authored/` separate.
- Hash sorted source paths, generated bytes, indexes, localization data, and
  voice metadata.
- Never modify authored source files during preparation.

## Test-first order

1. Add `@dialogue-wave1` feature scenarios for stable IDs, deterministic
   sorting, duplicate nodes, missing keys, malformed sources, and old
   manifests.
2. Add core unit tests in dedicated dialogue test modules.
3. Add preparation tests for path containment, fingerprints, diagnostics, and
   byte-identical repeated output.
4. Implement the contracts and preparation adapter.

## Acceptance gate

- Core compiles without Bevy or Yarn dependencies.
- Two identical preparations produce byte-identical dialogue artifacts.
- Duplicate or malformed Yarn content produces contextual diagnostics.
- Every source path is under the prepared asset root.
- Missing dialogue content is reported as loading/failed, never silently as an
  empty project.
- Requests before project readiness have a structured queue/reject result.

## Dependencies and exclusions

Depends on Wave 0. Does not add a persistent runner, production dialogue UI,
Fallout DIAL/INFO import, save records, or host functions.

Before the PR, write `DIALOGUE_WAVE1_MANUAL.md` if preparation or readiness
has a visible runtime/CLI surface. Record revision values in `Shipped
amendments`.
